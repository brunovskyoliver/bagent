## Decision

The rebuild ships through eight dependency-ordered stages. Each stage establishes one new authority, proves it, and removes the authority it replaces at an explicit exit boundary. Additive storage may coexist with legacy storage before a cutover, but lifecycle decisions never use dual writes or competing authorities.

### Current Stage 7C/8 qualification boundary

Stage 7C and Stage 8 signed/live qualification is limited to macOS 26. macOS
14 and 15 remain compile targets when the existing configuration permits them,
but this campaign makes no runtime, System Settings, TCC, visual, or
accessibility qualification claim for those versions. Live grant, denial,
revocation, and drag-to-System-Settings mutation are outside this campaign.
Deterministic permission adapters, signed-bundle and drag-payload validation,
privacy tests, and daemon-preserving relaunch remain required. An omitted
check is never PASS, and every release record must state this limitation.

## Gate vocabulary

There are three gate types:

- **Entry gate**: prerequisites that must be PASS before work in a stage may change an authority or schema.
- **Stage Exit gate**: evidence that the new stage authority is complete and its named legacy path has been removed.
- **Final Release gate**: whole-system qualification of the signed candidate across upgrade, recovery, accessibility, privacy, and live smoke boundaries.

Every criterion has exactly one verdict: **PASS**, **FAIL**, **BLOCKED**, or **UNVERIFIED**. A skipped test, zero-test execution, safe fallback, compilation failure, missing fixture, manual observation without the required deterministic evidence, or observational smoke alone is never PASS. Any release-blocking criterion left FAIL, BLOCKED, or UNVERIFIED prevents release.

## Migration, coexistence, and recovery contract

### Additive foundations

Stage 2 migrations add canonical Work, command-idempotency, revision, snapshot, outbox, cursor, generation, and recovery state without redirecting production writes. Existing storage and the unused foundations may coexist because only the legacy path is authoritative. Shadow or dual lifecycle writes are forbidden.

### Model Runtime atomic boundary

Stage 3 changes the port-8082 seam atomically. The coordinator owns speculative preload, leases, idle retirement, 35B retirement, poisoning, completion, and changed-PID restart decisions. Speculative preload has the lowest priority and owns no lease. Existing callers may temporarily use a typed-origin adapter, but cannot retain lifecycle authority. Port 8080 is outside scope and must remain untouched.

Rollback is allowed only when the coordinator proves zero leases and no transition in flight. Ambiguous BaseRT state is poisoned and recovered only by a clean changed-PID restart. The typed-origin adapter is removed at Stage 4 exit.

### Unified Work atomic boundary

Before Stage 4, the operator creates and verifies a pre-cutover database backup, dry-runs the migration on a copy, and proves restore. On startup, legacy admission closes before the migration establishes the schema generation, recovery generation, event cursor, and durable cutover marker. Routes open only after recovery completes.

Conversation Turns and admitted Automation Runs cut over together. Commands enter only through Work Coordinator. The first committed post-cutover Work establishes the downgrade boundary:

- Before that Work, the old binary plus the verified pre-cutover snapshot is an allowed rollback.
- After that Work, supported recovery is forward-only using the new schema and signed candidate.
- An unavoidable downgrade archives the current database, restores the pre-cutover backup, and explicitly discloses that post-cutover records are absent. It never tries to reinterpret new records with the old binary.

Pre-cutover terminal `automation_runs` are copied transactionally and idempotently into the canonical Legacy Run Record history table. They begin viewed, carry no Completion Attention, cannot Continue, and make no full Session Export claim. Only privacy-allowlisted summary text is retained; unsafe source text becomes a deterministic unavailable disclosure. Pre-cutover running rows and approvals become abandoned after the safe/changed-PID runtime boundary. Ephemeral chat state and UserDefaults identifiers are not migrated; Stage 7A creates an empty durable Current Chat when none exists.

### Session and chat migrations

Stage 6 makes Automation Session content immutable at terminal commit and separates mutable attention state. Retention is fifty sessions per automation and ninety days, without pruning active work or pending approvals. Deleting an Automation Definition stops future scheduling but does not cascade into Automation Sessions or Legacy Run Records.

Stage 7A atomically replaces Current Chat on `/clear`: old chat content and chat-scoped continuation context are removed in the same transaction that creates the fresh Current Chat. Automation Sessions and saved long-term memory are unaffected. Relaunch restoration always uses daemon-owned durable identity and content.

### Final contraction

After Stage 8 proves clean install, V14 upgrade, interrupted migration before and after commit, restore, rollback boundary, crash recovery, and schema checksums, a forward migration removes obsolete lifecycle columns and old run/session tables. Production code never reads or writes the protected pre-cutover backup. No runtime flag may reactivate an old authority. Legacy Run Records stay in their canonical table until ordinary 50/90 retention removes them.

## Release evidence record

Each executed criterion must retain: criterion ID, commit, environment and OS version, toolchain, fixture identity, start/end time, exact command or manual flow, nonzero case/assertion count where applicable, observed verdict, relevant artifact hashes, cleanup performed, and final runtime state. Evidence may link to privacy-safe logs or captures but must not embed credentials, raw tool arguments, hidden reasoning, private identities, or Evidence Content.

A baseline blocker is recorded against the criterion it blocks. It remains BLOCKED or FAIL until repaired and rerun. It cannot be promoted to PASS because the production app builds, a fallback is safe, another crate passes, or a live smoke looks correct.

The map's currently specified frontier is complete when this decision is accepted and issue 24 is closed. This decision authorizes no product-code change, dependency change, destructive migration, TCC mutation, protected runtime disruption, or map closure.
